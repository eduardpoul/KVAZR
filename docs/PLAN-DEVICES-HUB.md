# План: переход к Devices Hub

Ревизия построенного и план работ после нового дизайна.

Ветка: `feature/devices-hub`, отведена от `feature/core-foundation` (коммит `b743eb0`).
Дизайн: `Design/Devices Hub (test name)/Devices Hub.dc.html` — 30 артбордов, 10 итераций.
Предыдущий план: [PLAN.md](PLAN.md) — остаётся как запись сделанного, но больше не отражает цель.

---

## 1. Что изменилось

Прошлый план строил приложение под **одни наушники**. Новый дизайн — оболочка под **любую периферию любого вендора**: тот же дашборд, тот же список, те же карточки-строки для гарнитуры, мыши и клавиатуры. Меняется только набор непустых разделов.

Это не косметика. Однодевайсная модель зашита в домен: `DeviceState` — плоская запись с полями Maxwell, `IDeviceService` — единственный владелец единственного устройства с методами вида `SetChatMixAsync`. Всё это переделывается.

Хорошая новость: **протокольный слой не трогаем вообще**, а он самый дорогой в добыче.

## 4. Спецификация иконки трея изменилась

Текущий `TrayIconRenderer` рисует процент со сменой цвета по уровню заряда. Новый дизайн (`4a`, `4b`) задаёт другое:

- процент **без знака `%`** — на 16 px читаются только две цифры;
- заряд `100` — заполненная плашка **без цифр**;
- зарядка — точка в углу;
- нет данных — прочерк;
- плашка заливается акцентом, цифры выворачиваются — число остаётся читаемым на любой панели задач.

Артборд `4b` — увеличение 4× специально для проверки читаемости. Рендерер переписывается под это, размеры 16 / 20 / 24 / 32.

## 5. Главное архитектурное изменение

### Было

```
IDeviceService  ──  одно устройство, методы под Maxwell
    DeviceState ──  плоская запись: AmpGain, ChatMix, SidetoneLevel …
```

### Станет

```
IDeviceRegistry ──────── обнаружение, список, события подключения
    IDeviceSession ────── единственный владелец ОДНОГО устройства
        IDeviceDriver ─── audeze.race │ mock.mouse │ mock.keyboard
            Capability[] ─ дескриптор + значение
```

`Capability` несёт то, что описано в [CAPABILITIES.md](CAPABILITIES.md): `id`, примитив, диапазон, плюс обязательные атрибуты `status`, `access`, `rangeSource`, `volatile`, `reversible`, `risk`, `requires`. Страница устройства группирует их по доменам и рендерит примитивами. Ни одной страницы «под Maxwell» не остаётся.

**Драйвер снаружи отдаёт возможности, внутри остаётся типизированным.** RACE-код не превращается в словарь строк — он как был, так и остаётся, просто над ним появляется тонкий слой маппинга. Так абстракцию будет дёшево менять, когда появится второй настоящий драйвер и выяснится, что она в чём-то неправильная.

### Мок-драйверы

Мыши и клавиатуры физически нет, а экранов под них в дизайне десять. Поэтому: `mock.mouse` и `mock.keyboard` — драйверы, отдающие правдоподобный набор возможностей без всякого железа.

Это не костыль, а необходимость: без них половина дизайна непроверяема, и оболочка будет спроектирована под одно устройство заново. Помечаются как отладочные и не попадают в релизную сборку.

## 7. Новые открытые вопросы

**Профили существуют дважды.** В группе «Приложение» есть раздел «Профили» (`7a`), и одновременно профили есть у мыши (`9c`) и у клавиатуры (`10d`). Это разные сущности: первое — наборы настроек приложения с автопереключением по игре, второе — onboard-профили в памяти устройства. Названия совпадают, смысл нет. Нужно развести терминологию до реализации, иначе пользователь запутается.

**Иконка трея при нескольких устройствах.** Артборд `4c` намеренно показывает два решения. В `7a` есть настройка «Чей процент показывать → Основное устройство». Выбрать поведение по умолчанию.

**Горячие клавиши при нескольких устройствах.** `Ctrl+Alt+↑` меняет ChatMix — но у какого устройства? Дизайн не отвечает. Предложение: применять к основному устройству, тому же, чей процент в трее.

**Поиск в навигации.** Артборд `1a` показывает поле поиска вверху. Ищем по устройствам, по разделам или по настройкам — не определено.

**Имя приложения.** ~~В дизайне оно «Devices Hub (test name)».~~ **Закрыт в `design 2`: приложение называется KVAZR** — см. раздел 14.

## 8. Фазы

### Фаза A — модель устройств

Ядро. Всё остальное зависит от него.

- `DeviceId`, `DeviceInfo` (вендор, класс, изображение, транспорты)
- `Capability` — дескриптор плюс значение, атрибуты из CAPABILITIES.md §6
- `IDeviceDriver` — открыть, прочитать возможность, записать возможность
- `IDeviceSession` — единственный владелец устройства, сериализует доступ (сохраняет главное правило текущего `DeviceService`)
- `IDeviceRegistry` — обнаружение, список, события подключения и отключения
- Драйвер `audeze.race` поверх существующего `RaceSession`, без изменений в протоколе
- Мок-драйверы мыши и клавиатуры
- Обобщение HID-перебора: любой VID, не только `0x3329`

**Готово когда:** CLI перечисляет три устройства (Maxwell плюс два мока) и читает возможности через реестр; тесты на кодек по-прежнему зелёные.

### Фаза B — планировщик опроса

- Интервалы на устройство, приоритет активному
- Почти полная остановка при закрытом окне и флайауте
- Бэкофф после ошибок
- Настройка частоты из `7a`
- Правила порогов заряда — на устройство, с гистерезисом как сейчас

**Готово когда:** шесть устройств опрашиваются без роста нагрузки; тесты на пороги переписаны под несколько устройств и зелёные.

### Фаза C — дизайн-система

Самый большой кусок UI. Артборд `2a` целиком.

12 примитивов: `Readout`, `Toggle`, `Range`, `RangeGroup`, `Choice`, `Action`, `Curve`, `KeyMap`, `ButtonMap`, `Lighting`, `ProfileSet`, `HostSlots`.

8 состояний каждого: обычное, недоступно сейчас, непроверенная, идёт запись, ошибка записи, изменена извне, необратимая, опасная.

Правила языка из `2a`, соблюдать буквально:
- недоступность объясняется **рядом с контролом**, не баннером;
- непроверенная команда — янтарная точка, исчезает навсегда после первой успешной записи;
- ошибка живёт у контрола и возвращает прежнее значение;
- необратимость предупреждается **до** записи;
- красный только для настоящей ошибки записи и необратимых действий — **не для ограничений транспорта**.

**Готово когда:** есть страница-витрина, воспроизводящая `2a` один в один в обеих темах.

### Фаза D — оболочка и дашборд

- Навигация по схеме из раздела 3, поиск
- Дашборд «Все устройства»: `1a` и `1b`
- Страница устройства собирается из возможностей, разделы по доменам, пустые скрыты
- Пустое состояние `6c`

**Готово когда:** в окне переключаются Maxwell, мок-мышь и мок-клавиатура; разделы у всех трёх разные, оболочка одна.

### Фаза E — трей-поверхности

- Рендерер иконки по новой спецификации, размеры 16 / 20 / 24 / 32, обе темы, состояния из `4a`
- Флайаут 360 px, acrylic: `3a` одно устройство, `3b` три, `3c` шесть с прокруткой на потолке 600 px, `3d` светлая тема
- Попап подключения `3e`
- Тост низкого заряда `3f` — поверх готового `WindowsNotifier`

**Готово когда:** флайаут открывается по клику в трее и корректно ведёт себя на 1, 3 и 6 устройствах.

### Фаза F — разделы устройств

Maxwell на живом железе: Питание `8a`, Связь `8b`, Звук, Микрофон, Игра и чат `5a`, Дополнительно `8c`, плюс деградированные `5b` и `5c`.

Мок-устройства: мышь `6a`, `9a`–`9c`; клавиатура `6b`, `10a`–`10d`.

Кастомные контролы по возрастанию сложности: `Curve` (АЧХ), `HostSlots`, `ProfileSet`, `ButtonMap` (схема мыши с выносками), `KeyMap` (раскладка со слоями — самый большой контрол в приложении).

**Готово когда:** каждый раздел совпадает с артбордом и работает на живом Maxwell; мок-экраны отрисованы.

### Фаза G — разделы приложения

- Профили с разведённой терминологией (см. §7)
- Горячие клавиши поверх готового `WindowsHotkeys`, привязка к основному устройству
- Параметры `7a`: тема и системный акцент, язык, автозапуск, свёртывание в трей, порог заряда, частота опроса, чей процент в трее
- О программе `7b`

**Готово когда:** настройки переживают перезапуск, хоткеи ловятся при свёрнутом окне.

### Фаза H — тёмная тема и полировка

- Сверить `Tokens.axaml` с тёмными артбордами `1b`, `3a`–`3c`, раздел 10 — заменить выведенные значения на макетные
- Локализация ru / en
- Публикация

## 9. Риски

| Риск | Оценка | Что делаем |
|---|---|---|
| **Абстракция возможностей выведена из одного реального устройства** | **Высокий** | Ровно та ловушка, о которой сами предупреждали. Держим слой маппинга тонким, драйвер внутри типизированным. Первый настоящий второй драйвер почти наверняка потребует правок — закладываем это, а не сопротивляемся |
| **Мок-устройства уводят дизайн от реальности** | Средний | Мок отдаёт правдоподобные, но выдуманные значения. Экраны мыши и клавиатуры считаем непроверенными, пока не появится железо. В UI такие возможности помечены `status: untested` — механизм уже есть |
| **Объём фазы C** | Средний | 12 × 8 = 96 ячеек. Начинать с примитивов, которые нужны Maxwell (`Readout`, `Toggle`, `Range`, `Choice`, `Action`), сложные откладывать до фазы F |
| **Регрессии при переписывании `DeviceService`** | Средний | 387 строк рабочей логики с валидацией записи, отсечками и защитой от опасных команд. Переносим правила дословно, не переизобретаем. Чёрный список `0x1101` — в первую очередь |
| Расход при опросе N устройств | Средний | Фаза B делается до экранов, а не после |
| Тёмная тема расходится с задумкой | **Снижен** | Дизайн теперь содержит тёмные артборды |

## 10. Порядок

Фазы A и B — до всякого UI. Они переписывают домен и планировщик, и именно там регрессии дороже всего: там живут валидация записи, потолок гейна и чёрный список опасных команд.

Фаза C идёт третьей, потому что все экраны собираются из её контролов. Соблазн начать с дашборда — он красивый и быстро даёт картинку — приведёт к тому, что восемь состояний возможности всплывут позже и переломают вёрстку.

Начинать предлагаю с фазы A.

## 11. Перенесено с `feature/core-foundation`

Ветка `feature/core-foundation` продолжала жить параллельно. Что взято сюда:

| Коммит | Что даёт |
|---|---|
| Кроссплатформенный слой устройств | Linux hidraw: перебор через sysfs, транспорт через `ioctl`, выбор реализации по ОС. Плюс udev-правило в `packaging/` — без него доступ к hidraw закрыт, и приложение просто «не видит наушники» |
| Доставка тостов | Исправление времени жизни COM-апартамента |
| Проверка интеграции с Windows | Трей переживает сбой создания иконки и пишет об этом в лог |
| Публикация одним файлом | Self-contained сборка, сжатие выключено — оно вдвое поднимает резидентную память |

**Не взято: локализация.** Она переписывает восемь страниц, которых на этой ветке больше нет, — их заменила одна генерируемая страница устройства. Строковые файлы `Strings.ru.json` / `Strings.en.json` и `LocalizationService` останутся полезны, когда дойдёт до фазы H: забрать их отдельно, без привязки к удалённым вьюмоделям.

**Важно:** протокольный слой и весь путь к Maxwell по кабелю на обеих ветках **побайтово одинаковы**. Правок по работе с гарнитурой там не было — только новая платформа.

## 12. Что на Maxwell реально проверено

Список отдельный от [FEATURES.md](FEATURES.md) намеренно. Там сказано, что **известно** о протоколе; здесь — что **подтверждено на этом железе этими руками**. Разница между ними и есть янтарная точка в интерфейсе.

### Чтение — работает всё

Заряд, громкость и оба канала, баланс, ChatMix, сайдтон и его потолок, голосовые подсказки, пресет EQ, шумоподавление, мьют микрофона, прошивка. Проверяется одной командой:

```
kvazr --devices
```

### Запись — подтверждены две из шестнадцати

| Возможность | Sub | Чем подтверждено |
|---|---|---|
| Баланс чашек | `0x25` | `122 → 128` и обратно, с чтением после каждой записи |
| Голосовые подсказки | `0x20` | `12 → 11`, с чтением после |

### Запись — не проверялась ни разу

ChatMix, общая громкость, левый и правый канал, пресет эквалайзера, шумоподавление, сайдтон вкл/выкл, уровень сайдтона, уровень микрофона, таймер автовыключения, датчики head-tracking.

В интерфейсе все они несут янтарную точку. После первой удачной записи точка снимается навсегда и факт записывается в настройки — это и есть механизм превращения этого списка в предыдущий.

### Проверить нельзя сейчас

| Что | Почему |
|---|---|
| Уровень и мьют микрофона | Бум-микрофон отсоединён, устройство молчит на эти адреса |
| Head-tracking | Команда только на запись, обратного чтения нет — подтвердить результат нечем даже после удачной отправки |
| Что угодно по донглу | Устройство не отвечает ни на одну команду |

### По Bluetooth

Гарнитура отдаёт звук и заряд, настроек не отдаёт. Причина не в отсутствии канала —
канал есть и работает, — а в том, что протокол в нём чужой и нигде не описан. Полная
разведка в [BLUETOOTH.md](BLUETOOTH.md); коротко:

| Что | Итог |
|---|---|
| HID-профиль `00001124` | **отсутствует** — RACE-стеку не к чему приложиться |
| BLE-устройство по адресу | **нет**, ранняя догадка про «AirohaBLE» неверна |
| Вендорский RFCOMM `df21fe2c` | **работает**, но протокол собственный: RACE-кадры получают «не поддерживается» |
| Командная карта | **негде взять** — этот UUID не встречается ни в `Audeze.exe`, ни в `AirohaHidCoreLib.dll` |

Слепой перебор здесь опаснее, чем был по донглу: там мы знали, где лежит заводской
сброс, и обходили его. Здесь неизвестно ничего, и любой опкод может оказаться сбросом
или разрывом пары. Продолжать имеет смысл только после снятия HCI-лога мобильного
приложения Audeze — тогда работа станет обычной вместо угадывания.

### Проверять нельзя вообще

| Операция | Sub | Цена проверки |
|---|---|---|
| Сопряжение с донглом | `0x1101` / `0xAA` | Разрывает текущую пару. Сопрягать заново придётся вручную |
| Сброс к заводским | `0x1101` / `0x95` | Стирает всё, включая исправленный баланс |
| Любой гейн | `0x28` `0x29` `0x2A` | Первая запись необратимо защёлкивает зеркальный регистр `0x31`. Сейчас там нетронутое `0x8E`; вернуть можно только заводским сбросом |

Публичная документация протокола подписывает диапазон `0x1101` как «Battery/sync» — поэтому безобидный на вид read-sweep по нему однажды чуть не стёр гарнитуру.

### Как снимать янтарные точки

Схема на каждую безопасную возможность: прочитать → записать другое значение → прочитать → вернуть исходное. Семь возможностей проверяются так без последствий: ChatMix, пресет EQ, шумоподавление, сайдтон, уровень сайдтона, таймер, подсказки. Гейны и опасная тройка — нет.

### 14.3 Как поддерживать много устройств: четыре тира

Задача не в том, чтобы «поддержать» каждое устройство. Устройств бесконечно, каналов
четыре. **Приложение обязано быть полезным с пустым каталогом** — всё, что в каталоге,
это улучшение, а не условие работы.

**Тир 0 — то, что уже знает Windows. Покрытие 100 %.** Имя, класс, адрес, транспорт,
подключено или нет, и заряд у тех, кто его отдаёт. Ноль работы на устройство.
`WindowsBluetoothMonitor` уже ходит по `BTHENUM`/`BTHHFENUM` и читает
`DEVPKEY_Bluetooth_Battery` — он только зря захардкожен на `ProductMarker = "Maxwell"`.
Снять это ограничение, добавить обход USB HID через SetupAPI — и появляется драйвер,
находящий всё. Экраны `11c` и `11d` — это его экраны.

**Тир 1 — то, что знает класс. Сотни моделей на одну реализацию.** Четыре протокола, ни
один не привязан к вендору: VIA/QMK (usage page `0xFF60`), HID++ 2.0, XInput/DirectInput,
USB Audio Class плюс HID Battery page `0x85`. Четыре реализации закрывают больше
устройств, чем сорок вендорных.

**Тир 2 — то, что знает вендор.** Здесь живёт RACE. Дорого, потому что реверсится руками.
**Жёсткое правило: код пишется под протокол, модель — только данные.** Audeze — код,
потому что RACE пришлось вскрывать; вторая модель Audeze обязана быть строчкой в
каталоге. Знание для этого тира частично добыто чужими руками — HeadsetControl (~70
гарнитур), libratbag, OpenRGB. Они под GPL: **берём знание о протоколе, не код**, ровно
как сделали с RACE.

**Почему это вообще посильно.** Каталог может расти быстрее, чем наше железо, потому что
у возможности есть `status`, и непроверенная команда рисуется янтарной точкой. Запись в
каталоге для устройства, которого у нас нет, — не ложь, а честное «команда известна, на
живом не проверена»; первая успешная запись у пользователя точку снимает. Без этого
механизма поддержка чужого железа была бы враньём.

### 14.4 VIA — это каталог возможностей, а не картинок

Отдельно, потому что легко перепутать. Репозиторий `the-via/keyboards` — **1484
определения под `src/`, 3512 JSON всего**, разложены по вендорам (одна только Keychron —
115). Каждое определение содержит:

| Поле | Что даёт |
|---|---|
| `vendorId` / `productId` | ключ сопоставления, напр. `0x3434` / `0x02a0` |
| `name` | отображаемое имя |
| `matrix` | размер матрицы, `{rows, cols}` |
| `layouts.keymap` | **раскладка в формате KLE** — позиция, ширина, высота каждой клавиши |
| `lighting.underglowEffects` | список эффектов подсветки с их значениями |
| `customKeycodes`, `menus` | вендорские контролы, тоже данными |

То есть VIA закрывает примитивы `KeyMap` (`6b`, `10d`) и `Lighting` (`10c`) **живыми
данными для полутора тысяч клавиатур** — и не даёт ни одной фотографии.

Отсюда следствие, которое меняет план по картинкам: **клавиатуре фотография не нужна.**
Из `layouts.keymap` рисуется настоящая раскладка — она и точнее, и полезнее, и в строке
56 px мини-раскладка отличает 75 % от 60 % и от полноразмерной, чего фотография не
делает. Фотография остаётся только героем на странице устройства.

### 14.5 Откуда берётся определение клавиатуры

Порядок ровно такой же, как везде: **сначала работает без данных, потом становится
красивее.** «Пусть юзер сам загрузит» — последняя ступень, а не первая.

**Ступень 0 — протокол без определения.** Клавиатура с usage page `0xFF60` отвечает на
`id_get_protocol_version`, и дальше весь протокол VIA работает **на любой плате без
всякого JSON**: чтение и запись кейкодов по `(слой, ряд, колонка)`, число слоёв, эффекты
подсветки по индексу. Уже на этом уровне страница показывает «Слой 0, матрица 6×15» и
даёт менять клавиши. **Определение не открывает функциональность — оно превращает матрицу
в картинку твоей клавиатуры** и подставляет человеческие имена эффектам.

**Ступень 1 — индекс в сборке.** С приложением едет компактный индекс `VID:PID → id
определения`, не сами определения. Полторы тысячи записей — это десятки килобайт, а не
мегабайты.

**Ступень 2 — определение по требованию.** Нашли совпадение в индексе — тянем один файл с
того же CDN, что и картинки, и кладём в локальный кэш навсегда. Зеркалим у себя, а не
ходим в `the-via/keyboards` напрямую: иначе переименование файла вверху по течению
ломает нас у пользователя.

**Почему определения нельзя класть в сборку.** `the-via/keyboards` — **GPL-3.0**, 11 МБ.
На данные такая лицензия ложится неудобно, но всерьёз: положить их внутрь нашего
дистрибутива значит распространять GPL-контент вместе с ним. Поэтому граница проводится
физически: определения живут в **отдельном каталожном репозитории со своей лицензией
GPL-3.0 и своими notice-файлами**, а приложение забирает их оттуда в рантайме и держит в
пользовательском кэше. В нашей сборке — только индекс `VID:PID → id`, то есть перечень
аппаратных идентификаторов: факты, а не выражение.

То есть CDN для клавиатурных определений — **не оптимизация «чтобы exe не пух», а
требование лицензии**. Картинки при этом остаются в сборке: у них происхождение своё и к
VIA отношения не имеет. Два разных механизма по двум разным причинам, и путать их нельзя.

**Ступень 3 — вендорские определения.** NuPhy в общий репозиторий не входит, она публикует
свои JSON сама, на `nuphy.com/pages/json-files-for-nuphy-keyboards`. Такое подтягивается в
наш каталог один раз человеком, тем же PR, что и картинка. То есть **для NuPhy Air75 V2
пользователю не придётся делать ничего** — определение будет лежать у нас.

**Ступень 4 — файл пользователя.** «Файл определения…», выбрать JSON, который дал вендор.
Хранится локально по `VID:PID`. Это не костыль: ровно такая же кнопка есть в самой VIA,
потому что новые платы всегда появляются раньше любого каталога. Рядом — «предложить в
общий каталог».

Итог для вопроса «поставил софт, воткнул NuPhy»: клавиатура опознаётся сразу по
дескриптору, раскладка приезжает из нашего зеркала, руками не делается ничего. Если плата
совсем свежая и её нет нигде — она **всё равно настраивается**, просто вместо картинки
клавиатуры будет сетка матрицы, и появится предложение подложить файл.

### 14.6 Картинки: три источника, тот же порядок деградации

Дизайн вопрос не решает — все восемь новых устройств стоят пустыми `<image-slot>`,
которые заполняются перетаскиванием в редакторе. Настоящие фотографии есть только у
Maxwell. Общего API продуктовых фотографий периферии не существует: у Wikimedia лицензия
чистая, но покрытия нет; штрихкодовые базы требуют EAN, которого USB не даёт; вендорские
CDN — это хотлинк, который ломается.

Порядок разрешения — тот же, что у возможностей:

1. **Курируемое фото по ключу каталога.** Сейчас в сборке, дальше — репозиторий на
   гитхабе через jsDelivr, тем же каналом, что и каталог, чтобы картинка и способности не
   могли разойтись.
2. **Силуэт по классу.** Не извинение, а решение. Десяток векторных глифов в стиле KVAZR.
   В строке 56 px плитка занимает 32–40, и на таком размере хороший силуэт читается лучше
   фотографии. Список из восьми устройств, где одно — фото на белом фоне, а семь глифы,
   выглядит хуже, чем восемь одинаковых глифов.
3. **Файл пользователя.** Правый клик → «Подобрать изображение…», хранится локально.
   Рядом — «предложить в общий каталог», открывающее заготовленный PR. Так «человек
   грузит сам» перестаёт быть костылём и становится тем, за счёт чего каталог растёт.

**Ключ — не VID:PID.** Bluetooth-устройства USB-идентификаторов не имеют, а AirPods
опознаются вообще иначе. Ключ каталога — `<вендор>-<модель>` в виде слага, а VID:PID и
BT-матчеры лежат внутри записи как правила сопоставления. Так же устроены и libratbag, и
VIA.

### 14.7 Что скачано и почему именно столько

Шесть изображений, **120 КБ на все**, 512×512 WebP, фон выбит, предмет по центру с полем
6 %: `audeze-maxwell`, `logitech-g-pro-x-superlight-2`, `hyperx-quadcast-s`,
`nuphy-air75-v2`, `nuphy-halo75-v2`, `flydigi-apex-5`. Происхождение и лицензия каждого —
в `src/Kvazr.App/Assets/Devices/images.json`.

**Отсюда ответ про exe.** Шесть устройств — 120 КБ; self-contained сборка .NET весит
60–80 МБ. Класть в сборку, CDN включать, когда счёт пойдёт на сотни. Но резолвер писать
трёхисточниковым сразу, чтобы переключение стало правкой конфига, а не переделкой.

**Два устройства сознательно без фото.** AirPods Pro 2 — единственное свободно
лицензированное фото это снимок с рук на столе, а свои изображения Apple не отдаёт.
JBL Flip 6 — `jbl.com` отклоняет автоматические запросы на всех региональных хостах, а на
Commons есть только Flip 3 и Flip 4. Оба — устройства, из которых мы только читаем, и оба
получают силуэт класса. Это не пробел: именно так будет выглядеть хвост каталога, и
дизайн теперь показывает оба поведения сразу.

Проверено экспериментом, а не рассуждением: первая сборка включала фото с Wikimedia для
мыши и наушников — розовая мышь рядом с коробкой и наушники на сером столе. Рядом со
студийными снимками они выглядели поломкой. Отсюда правило в `images.json`: **фотография,
которую нельзя привести к общему виду, не добавляется — силуэт лучше.**

### 15.2 Три бага, которых не было бы видно из исходников

**Диалог подтверждения падал.** Генератор Avalonia выпускает
`InitializeComponent(bool loadXaml = true)`, и написанный руками
`private void InitializeComponent()` рядом с ним компилировался и выигрывал вызов —
все поля `x:Name` оставались null. В `ConfirmDialog` это означало исключение при первом
же обращении к необратимой возможности, то есть при попытке сбросить наушники к
заводским настройкам. Исправлено там же и в `MainWindow`, `SplashWindow`.

**`DevicesChanged` — не сигнал об окончании поиска.** Реестр поднимает его, когда
меняется снимок сессии, поэтому на машине, где ничего не подключено, он не срабатывает
никогда. Всё, что ждало бы его, показало бы ошибку ровно там, где «устройств нет» —
правильный ответ. Обойдено через `FirstSweep`; правильное место для этого —
`DiscoveryCompleted` на самом реестре, см. 15.4.

**Тема из настроек не могла победить.** `FluentAvaloniaTheme PreferSystemTheme="True"`
переприменяет системную тему уже после `App.ApplyTheme`, так что сохранённый выбор
Light или Dark молча терялся. Латентно только потому, что экрана настроек ещё нет.
Выключено; следование системе осталось — это и есть `ThemeVariant.Default`.

### 15.4 Что осталось и где

## 16. Иконка трея: процент убран

Артборды `4a` и `4c` рисовали в трее процент заряда, и для приложения про одни наушники
это было правильно. С восемью подключёнными устройствами такого числа нет: любое,
которое покажет иконка, будет чужим большую часть времени, а выбор между «основным
устройством» и «самым низким зарядом» из `4c` только переносит неправильность с места на
место, а не убирает её.

Решение: **в трее всегда знак KVAZR.** Он отвечает на вопрос, который переживает переход
к многим устройствам — просит ли что-нибудь внимания, — и делает это цветом планеты, а
не чтением цифр.

Числа переехали в подсказку: устройства, которые сообщают заряд, самое разряженное
первым, не больше четырёх строк. Подсказка Windows — это маленькая рамка под курсором, и
список из восьми строк в ней никто не читает.

Что удалено вместе с этим: рисование плашки с цифрами (`TrayIconRenderer.Draw` и его
помощники), сетка процентов в `--dump-icons`, настройки `ShowPercentageInTray` и
`TrayPercentFrom`, и секция «Иконка трея» на экране параметров. Пять состояний знака и
шестое, «ошибка связи», остались — они и есть то, что иконка теперь говорит.

Это отменяет пункт «чей процент в трее» из списка открытых вопросов §13: вопрос снят, а
не отвечен.

## 17. Тир 1 на паузе: некому ответить

`--hid` показывает, что на этой машине из классовых протоколов есть только HID++:
VIA-устройств (`0xFF60`) нет ни одного, донгл NuPhy отвечает на своей вендорской
странице `0xFF31`.

HID++ реализован в части чтения и доходит до железа. Приёмник Logitech отвечает на
чтение регистра сразу; все шесть слотов отвечают ошибкой «занято — устройство не
отвечает». То есть канал и протокол рабочие, а привязанного и не спящего устройства
Logitech на приёмнике сейчас нет.

Драйвера намеренно нет: его путь чтения ни разу не вернул настоящее устройство.
Пробник `--hidpp` остаётся точкой, с которой это доделывается за один заход, как только
появится живое устройство — имя, тип, заряд уже написаны.

**Что здесь было выяснено и стоит помнить:**

- Ответ приходит только на ту коллекцию, которой принадлежит его report id. В Windows
  короткие и длинные отчёты HID++ — разные top-level collections, то есть разные пути
  устройств. Запрос в длинный интерфейс и ожидание там дают тишину от приёмника,
  который на короткий отвечает мгновенно.
- Запрос обязан быть ровно той длины, которую объявляет интерфейс: HID отклоняет
  короткий буфер, а не дополняет его.
- Чтение блокирующее, отменяется `CancelIoEx`. `ReadFile` в полёте вешает
  `CloseHandle` — это дедлок при выходе, а не медленное завершение.

VIA ждёт клавиатуру, подключённую кабелем: у NuPhy определения публикуются отдельно, а
usage page `0xFF60` через донгл не выставляется.

## 18. UI переезжает в веб: BlazorWebView внутри Avalonia-оболочки

Решение пользователя после очного сравнения (22.08.2026): секция «Звук», свёрстанная в
HTML за пятнадцать минут, совпала с макетом точнее, чем Avalonia-вёрстка после дня
правок — потому что макет и написан в HTML, и числа переносятся без пересчёта в чужую
систему координат.

Как это устроено:

- **Оболочка остаётся Avalonia**: окно, трей, флайаут, глобальные хоткеи, тосты,
  сплэш. Ничто из этого не хочет быть веб-страницей, и всё это уже работает.
- **Контентная панель — один BlazorWebView** (WinForms-хост через NativeControlHost,
  HWND). Один на всё окно и на всю жизнь окна: WebView грузится секунды, и платить их
  на каждый клик по рельсе нельзя. Корневой компонент `PaneRoot` сам слушает
  `ShellViewModel.CurrentPage` и меняет страницы.
- **Прямой биндинг**: проект переведён на `Microsoft.NET.Sdk.Razor`, компоненты лежат
  в `src/Kvazr.App/Web/` и работают с теми же вью-моделями, что и нативные вью.
  Никаких адаптеров. Записи уходят через `Dispatcher.UIThread.Post` — тот же путь,
  те же подтверждения.
- **Токены — один источник**: `tools/design-tokens.py` теперь пишет и
  `wwwroot/css/tokens.css` (размеры из макета + палитра из `Themes/Tokens.axaml`).
- **Иконки устройств** — цветной Fluent 2 набор из `Design/kvazr/device-icons`
  (рисунки Microsoft, где они есть, остальные по тем же правилам), собирается
  `kvazr --fluent-icons` в `Web/FluentIcons.g.cs` и `Themes/FluentIcons.axaml`. Выбор
  ключа — `Web/DeviceIcon.cs`: класс устройства + подсказки из имени.
- **Фолбэки**: `--native` возвращает Avalonia-вьюхи целиком; на не-Windows они же —
  вся история, пока нет WebKit-хоста. Внутренние страницы (идентика, матрица
  контролов) остаются нативными всегда.
- **Капризы, уже пойманные**: `blazor.webview.js` — static web asset и ищется через
  манифест по имени entry-сборки; несётся явным файлом в `wwwroot/_framework/`.
  WinForms SDK впрыскивает global usings (`Application`, `Color`, `Point` бьются с
  Avalonia) — сняты `<Using Remove>`. Скриншотный дамп не видит чужой HWND — все
  проверки веб-страниц только оконным захватом (`grab.ps1`).

Замер памяти Debug-сборки (WS): нативно ~187 МБ; с WebView ~207 МБ + ~320 МБ на
6 процессов WebView2. Пользователь считает это приемлемым; релизный замер — после
стабилизации.
