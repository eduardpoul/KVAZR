# План: базовые устройства — драйверы по классам

Как довести приложение до состояния «любая мышь, клавиатура, гарнитура, микрофон
и геймпад на столе отдают данные, а где протокол позволяет — принимают настройки»,
не реверся каждую модель по отдельности.

Ветка: `feature/base-devices`, отводится от `feature/devices-hub`.
Предшественники: [CLASS-PROTOCOLS.md](CLASS-PROTOCOLS.md) — разведка протоколов,
[BASELINE-CAPABILITIES.md](BASELINE-CAPABILITIES.md) — что рисовать,
[ARCHITECTURE.md](ARCHITECTURE.md) — куда класть код.
Этот документ отвечает на третий вопрос: **что писать и в каком порядке**.

---

## 1. Ревизия: что есть в коде, а не в документах

Разница существенная. Разведка по классам сделана и записана подробно, но
**в приложении из шести классовых дверей открыта ровно одна, и та наполовину**.

| Протокол / API | Разведка | Пробник в CLI | Драйвер в приложении |
|---|---|---|---|
| Core Audio (громкость, mute, пик) | да | `--audio`, 195 строк | **нет** |
| XInput / WGI (геймпады) | да | `--xinput`, 114 строк | **нет** |
| VIA / QMK / Vial (клавиатуры) | да | — (нет железа по кабелю) | **нет** |
| HID++ 2.0 (Logitech) | да | `--hidpp`, 193 строки | **частично**: заряд и зарядка, только чтение |
| BLE-реклама Apple (AirPods) | да | `--airpods`, 92 строки | **нет** |
| Switch Pro | протокол + тесты готовы | — | **нет** |
| HID Battery Strength (усаж) | **не сканировали** | нет | нет |
| BT-заряд из свойств Windows | да | — | **есть** (тир 0) |
| RACE (Audeze) | да | много | **есть**, полный |

Пробник — это не драйвер: он печатает в консоль и умирает. Между `--audio`
и строкой громкости на странице устройства лежит вся работа этого плана.

**UI при этом не узкое место.** Все двенадцать примитивов имеют вью-модели
(`CapabilityComposites.cs`, `CapabilityPrimitives.cs`) и рендерятся вебом
(`Web/Controls/CapRow.razor`) — включая `Lighting`, `ButtonMap`, `KeyMap`,
`ProfileSet`, `HostSlots`, `Curve`. Как только драйвер объявит возможность,
её нарисуют. Ждём драйверы, а не экраны.

## 2. Матрица «класс × транспорт»: что физически доступно

Главный вопрос — «клавиатуры по блютузу и донглу, уши по блютузу и донглу» —
распадается на транспорты, и ответы по транспортам разные. Ниже только то, что
достижимо **без вендорского реверса**.

### Гарнитуры и наушники

| Транспорт | Что даёт база | Чем |
|---|---|---|
| Bluetooth | заряд (если устройство его отдаёт), громкость, mute, живой пик, микрофон | свойство Windows + Core Audio |
| 2.4G донгл | громкость, mute, пик; **несколько именованных выходов** (Game/Chat — донгл выставляет их разными конечными точками) | Core Audio |
| Кабель USB | то же, что донгл | Core Audio |
| BLE (AirPods) | заряд L / R / кейс + флаги зарядки | реклама Apple 0x07 |

**Заряда по донглу и кабелю базово нет.** Донгл — это USB-звуковая карта, она
не обязана ничего знать про батарею наушников. Заряд по этим транспортам —
всегда вендорский протокол (у нас это RACE). Врать про это в UI нельзя.

### Мыши

| Транспорт | Что даёт база | Чем |
|---|---|---|
| Донгл Logitech | заряд, зарядка, имя, тип, прошивка; **DPI, частота опроса, профили в памяти, назначение кнопок, режим питания, высота отрыва, подсветка** | HID++ |
| Кабель (Logitech) | то же — мышь отвечает на прямой индекс `0xFF` | HID++ |
| Bluetooth | имя, класс, заряд если отдаёт | тир 0 (BT-свойство / GATT 0x180F) |
| Донгл или кабель прочих вендоров | имя, класс, подключение | тир 0 |

HID++ по Bluetooth формально существует (те же коллекции `0xFF00`), но у нас
не проверен — отдельный пункт проверки в §8.

### Клавиатуры

| Транспорт | Что даёт база | Чем |
|---|---|---|
| Кабель (VIA/QMK) | слои и раскладка (**чтение и запись**), макросы, подсветка, живая матрица нажатий | VIA `0xFF60` |
| Кабель (Vial) | то же + определение раскладки **из самой прошивки** | Vial |
| Донгл 2.4G | имя, «USB-донгл» — и всё | тир 0 + снимок с кабельной сессии |
| Bluetooth | заряд | тир 0 |
| Донгл Logitech | заряд, прошивка, профили и подсветка у моделей с ними | HID++ |

**VIA через 2.4G-донгл не идёт** — проверено на NuPhy трижды, и это общий
случай, а не особенность модели. Заряда донгл тоже не выставляет. Отсюда
модель «кабельная сессия → снимок → read-only на донгле с датой», описанная в
CLASS-PROTOCOLS.md: раскладка живёт в клавиатуре и по донглу **применяется**
всегда, мы просто не можем её оттуда прочитать и изменить.

### Геймпады

| Транспорт | Что даёт база | Чем |
|---|---|---|
| Любой (донгл, кабель, BT) | подключён, тип пада, живые стики/кнопки/триггеры, вибрация двумя моторами | XInput |
| Xbox wireless | + заряд, + вибрация триггеров | WGI |
| Switch Pro (BT сразу, USB после рукопожатия) | заряд (4 ступени), прошивка, **цвет корпуса**, индикатор игрока, вибро, калибровка стиков | свой протокол, уже написан и покрыт тестами |
| DualSense / DS4 | заряд, гироскоп, тачпад, адаптивные триггеры, подсветка | открытый HID-лейаут |
| Донглы сторонних (Flydigi и подобные) | заряда нет — донгл врёт «проводной» | только вендорский канал |

**Лепестков в XInput не существует** — пад отрабатывает их сам, подменяя
кнопками. Это не наша недоработка и не чинится классовым протоколом.

### Микрофоны

| Источник | Что даёт |
|---|---|
| Core Audio | уровень записи, mute, живой пик, громкость мониторинга |
| HID-страница телефонии `0x000B` | tap-to-mute (касание сверху) — у QuadCast есть |
| Вендор | RGB, аппаратный gain, диаграмма направленности |

### Колонки и ЦАПы по кабелю

Core Audio целиком: громкость, mute, пик. Отдельного класса не нужно — тот же
аудио-модуль, другая категория в UI.

### Поверх всех классов

**Батарейный усаж HID** (`0x0006`/`0x20` Battery Strength, страницы `0x84`/`0x85`)
читается `HidP_GetValueCaps` и `HidP_GetUsageValue` без единого вендорского
байта. Сейчас перечислитель читает только `HidP_GetCaps` — верхнюю коллекцию —
и батарейных значений не видит вовсе. Это самая дешёвая универсальная находка
в списке: любое устройство, объявившее усаж, получает заряд бесплатно.

## 3. Блокер, который надо снять первым: одно устройство — один драйвер

`DeviceRegistry.DiscoverAsync` собирает находки в `found[info.Key] = (info, driver)`,
затем `Shadowed()` выбрасывает всё, что нашёл драйвер тиром ниже. Сессия
создаётся **одна на устройство, с одним соединением**. Победитель забирает всё.

Для тира 0 против тира Class это правильно: «USB Receiver» должен уступить мыши.
Но половина этого плана — не находилки устройств, а **поставщики возможностей
для уже найденного устройства**, и нынешний контракт их не принимает:

- **Core Audio не сможет добавить громкость Windows на страницу Maxwell.** RACE —
  тир Vendor, аудио — тир Class; выиграет RACE, и аудио-строки просто исчезнут.
- **Заряд с дока Flydigi некуда положить** — строку геймпада держит XInput или тир 0.
- **Tap-mute с телефонной страницы не приклеить** к строке QuadCast, которую
  держит Core Audio.
- **Универсальный батарейный усаж не добавить никому** — он ничей.

### Что делаем

Разводим два разных вопроса: *кто владеет устройством* и *кто добавляет ему строки*.

```csharp
// Остаётся как есть: находит и владеет.
public interface IDeviceDriver { … }

// Новое: ничего не находит, дополняет найденное.
public interface ICapabilityContributor
{
    string ContributorId { get; }

    /// Есть ли что сказать про это устройство. Решение — по HardwareIds,
    /// тем же, по которым реестр уже склеивает донгл с кабелем.
    Task<IDeviceConnection?> AttachAsync(DeviceInfo device, CancellationToken ct = default);
}
```

`DeviceSession` держит одно основное соединение и N дополняющих: `Capabilities` —
конкатенация, чтение и запись маршрутизируются по id возможности (владелец id —
тот, кто её объявил), конфликт id разрешается в пользу основного с записью в лог.
Тирование и затенение остаются **только между основными**.

Опрос: дополняющие идут через тот же планировщик, но со своими интервалами —
пик-метру Core Audio нужны 10 Гц при открытой странице, батарее хватает 30 секунд.
`PollingAttention` уже умеет разделять это.

**Готово когда:** тест, где мок-дополнитель добавляет строку к мок-устройству и
запись уходит именно ему; на живом Maxwell на странице появляются системная
громкость и mute Windows — **рядом** с аппаратной громкостью RACE, не вместо неё.

Это фаза 0, и её нельзя переставить: без неё три модуля из восьми придётся
переписывать сразу после написания.

## 4. Восемь модулей

Раскладка по папкам — из [ARCHITECTURE.md](ARCHITECTURE.md): `Shared/` — один код
на класс, `Device/` — один вендор ради глубины.

| Модуль | Папка | Роль | Покрытие |
|---|---|---|---|
| `audio` | `Shared/Audio` | дополнитель | гарнитуры, микрофоны, колонки — любой транспорт |
| `hid.battery` | `Shared/Hid` | дополнитель | любое устройство с батарейным усажем |
| `logitech` | `Shared/Logitech` | драйвер (есть, дописать) | мыши и клавиатуры Logitech |
| `gamepad` | `Shared/Gamepad` | драйвер | всё XInput/WGI-совместимое |
| `via` | `Shared/Keyboard` | драйвер | VIA/QMK/Vial по кабелю |
| `apple` | `Device/Apple` | драйвер | AirPods, Beats |
| `nintendo` | `Device/Nintendo` | драйвер | Switch Pro |
| `flydigi` | `Device/Flydigi` | дополнитель | APEX 5 — заряд с дока |

### 4.1 `audio` — Core Audio

Самый выгодный модуль: один код закрывает три категории из брифа сразу и
работает по любому транспорту, потому что Windows уже всё нормализовала.

Что читает и пишет: громкость и mute на каждой конечной точке
(`IAudioEndpointVolume`), живой пик (`IAudioMeterInformation`), уровень записи и
мониторинга. Привязка к строке устройства — через `ContainerId`, ту же величину,
по которой тир 0 группирует узлы; значит `HardwareIds` совпадут и склейка
заработает без нового механизма.

Тонкость, которую надо заложить сразу: у одного устройства бывает **несколько
именованных выходов** (у гарнитуры с донглом — Game и Chat). Это не одна строка
громкости, а по строке на выход, с именем от Windows.

COM-интерфейсы уже описаны в `Cli/AudioProbe.cs` — переносим, а не пишем заново.

**Готово когда:** у QuadCast на странице есть вход, mute и живой пик; у Maxwell —
системная громкость рядом с аппаратной; у колонок по кабелю — своя строка.

### 4.2 `hid.battery` — универсальный заряд

Расширить `WindowsHidEnumerator`: после `HidP_GetCaps` пройти
`HidP_GetValueCaps` по всем коллекциям и запомнить, кто объявил
`0x0006`/`0x20` или страницы `0x84`/`0x85`. Дополнитель читает
`HidP_GetUsageValue` и отдаёт `PowerBattery`.

Дёшево, строго по стандарту, и покрывает устройства, о которых мы никогда не
услышим. Сначала сканер и вывод в `--hid`, чтобы увидеть, кто на этом столе
вообще объявляет усаж, и только потом дополнитель.

### 4.3 `logitech` — дописать HID++ до записи

Сейчас драйвер читает заряд и зарядку и **сознательно ничего не пишет**.
Superlight 2 отдала 33 фичи; из них к реализации:

| Фича | Возможность | Примитив |
|---|---|---|
| `0x2202` ExtendedAdjustableDPI | ступени DPI, текущая, X/Y | Range или Choice |
| `0x8061` ExtendedReportRate | 125 Гц … 8 кГц | Choice |
| `0x8090` ModeStatus | режим производительность/выносливость | Toggle |
| `0x2251` LiftDetection | высота отрыва | Choice |
| `0x8100` OnboardProfiles | профили в памяти мыши | ProfileSet |
| `0x1b04` ReprogrammableKeys | назначение кнопок | ButtonMap |
| `0x8070` / `0x8071` | подсветка у моделей с ней | Lighting |
| `0x0003` DeviceInfo | прошивка | Readout |

Порядок — ровно этот: сверху дёшево и полезно, снизу дорого и редко.
Первые четыре — простые регистры, последние три — структуры.

Два обязательных условия. Первое: **лейаут ответа `0x2202` сверить с Solaar**
перед первой записью — наш парс уже выдал бессмыслицу («3 / 45062»), raw в
пробнике печатается специально для сверки. Второе: любая первая запись выходит
со статусом `Untested` (янтарная точка), снимается после подтверждения на живом.

Фичи `[hidden]` и `[eng]`, а также DFU `0x00C3` / `0x00D0` — не трогаем принципиально.

### 4.4 `gamepad` — XInput + WGI

Два API в одном драйвере: XInput даёт слот, тип, состояние и вибрацию;
WGI (`Windows.Gaming.Input`) добавляет батарейный отчёт, вибрацию триггеров и
`RawGameController` для падов, не влезающих в стандартный лейаут.

Возможности: подключение и тип (Readout), вибротест (Action), живая диагностика
стиков и кнопок (Readout — это ещё и тестер дрейфа, реальная польза), заряд
там, где он настоящий.

Отдельная работа — **живая диагностика**: это первая возможность, которую надо
обновлять с частотой кадра, а не опроса. Читается через тот же
`PollingAttention.Focused`, но с интервалом порядка 60 мс и только при открытой
странице. Заодно проверим, что схема выдерживает такую нагрузку.

Заряд не показываем там, где его нет: сторонние донглы отвечают «проводной,
батареи нет», и рисовать пустую строку хуже, чем не рисовать никакой.

### 4.5 `via` — клавиатуры по кабелю

Драйвер по usage page `0xFF60` usage `0x61`, 32-байтные отчёты, запрос-ответ.
Рукопожатие определяет диалект: Vial (определение из прошивки) или VIA
(определение из базы).

Возможности: число слоёв и кеймап (KeyMap, чтение и запись), макросы,
подсветка (Lighting: яркость, эффект, цвет), живая матрица нажатий (тестер).

Данные раскладки — отдельный конвейер: команда `maxwell --via-definitions`
собирает индекс VID:PID → определение из `the-via/keyboards` (MIT, около
полутора тысяч определений) и кладёт в ресурсы; рантайм-фолбэк докачивает одно
определение по id; последняя ступень — импорт JSON руками. **Без определения
драйвер всё равно полезен**: слои, макросы, свет и тестер — это протокол, а не
JSON; нет только рисунка клавиатуры.

Конвейер пишется на C# внутри `Maxwell.Cli`, а не скриптом на стороне: питон в
этом проекте только для тестов, и заводить ради одного генератора вторую
цепочку инструментов незачем. Существующие `tools/design-tokens.py` и
`tools/fluent-icons.py` — наследие, новые так не делаем.

Плюс модель снимка: кабельная сессия сохраняет прочитанное под ключом
устройства, на донгле страница показывает снимок read-only с датой и строкой
«подключите кабель, чтобы изменить».

Реализуется под кабель — на этом столе VIA-устройств по кабелю сейчас нет,
поэтому драйвер пишется против тестов на документированных байтах (как
`SwitchPro.cs`), а живая проверка — первым же кабелем.

### 4.6 `apple` — AirPods

BLE-наблюдатель в фоне, декодер рекламы `0x07` уже написан в `--airpods`.
Три Readout: левый, правый, кейс, плюс флаги зарядки. Привязка к строке —
эвристическая (модель и близость по RSSI), потому что Apple ротирует MAC;
это надо честно пометить в UI, как делают все такие утилиты.

Больше Apple не отдаёт ничего — ни GATT, ни свойства Windows.

### 4.7 `nintendo` — Switch Pro

Протокол готов и покрыт тестами до байта. Остаётся драйвер: поиск по
`057e:2009`, рукопожатие на USB (`80 02`, затем `80 04`), перевод в режим `0x30`,
и возможности — заряд, прошивка, цвет корпуса из SPI (можно красить строку),
индикатор игрока (Choice, первая запись — янтарём), вибротест, калибровка.

Ждёт железо; чек-лист первой встречи — VERIFY-LATER п. 6.

### 4.8 `flydigi` — заряд с дока (трек A)

Пассивный дополнитель: открыть `0xFFA0` дока, читать без записи, разобрать кадр
`5A A5`. Даёт заряд на строке APEX 5, когда пад стоит на зарядке. Блокер —
одно наблюдение у стола (VERIFY-LATER п. 1): снять пад и увидеть, какой из
двух байтов замрёт.

Трек B (реверс Flydigi Space: лепестки, триггеры, гироскоп, профили) — не в
этом плане. Один перехват открывает его целиком, но это отдельный вечер.

## 5. Фазы и порядок

| Фаза | Что | Зависит от | Готово когда |
|---|---|---|---|
| **0 ✅** | Дополнители: несколько источников возможностей на одно устройство | — | мок-дополнитель проходит тесты; у Maxwell системная громкость рядом с аппаратной |
| **1 ✅** | `audio` — Core Audio | 0 | микрофон, гарнитура и колонки имеют рабочие страницы громкости |
| **2** | `hid.battery` — сканер усажей и дополнитель | 0 | `--hid` печатает, кто объявляет батарейный усаж; заряд появляется без вендорского кода |
| **3** | `logitech` — DPI, частота, режим, отрыв (запись) | — | DPI меняется из приложения и сохраняется в мыши; проверено выключением приложения |
| **4** | `gamepad` — XInput/WGI, вибротест, живая диагностика | — | APEX 5 вибрирует по кнопке, стики видны живьём, заряд показан только там, где он настоящий |
| **5** | `logitech` — профили и кнопки | 3 | ProfileSet и ButtonMap работают на живой мыши |
| **6** | `via` и конвейер определений | — | против тестов; на живом кабеле — слои и подсветка |
| **7** | Особые: `apple`, `nintendo`, `flydigi` | 0 | по мере железа и одной проверки у стола |

Порядок обоснован так: фаза 0 — фундамент; фаза 1 — самая большая польза на
единицу работы (три категории устройств разом); фазы 3 и 4 не зависят от
механики дополнителей и могут идти параллельно; фаза 6 самая крупная и упирается
в кабель, поэтому не первая.

### Сделано в фазах 0 и 1

**Фаза 0.** Рядом с `IDeviceDriver` появился `ICapabilityContributor` — один метод
`AttachAsync`, решение по `HardwareIds`. `DeviceSession` держит основное соединение
плюс N дополняющих, `_owner` маршрутизирует чтение и запись по id возможности,
порядок каналов ставит владельца первым, поэтому спорный id достаётся ему.
Отдельная поправка, которая понадобилась сразу: раньше `IOException` на чтении
означал «устройство пропало» и обрывал весь обход; теперь падает только тот канал,
который отказал, а его строки остаются с последним значением и переподключаются
следующим проходом. Девять тестов.

**Фаза 1.** `Maxwell.Race/Windows/WindowsAudioEndpoints.cs` — Core Audio;
`Core/Drivers/Shared/Audio/` — дополнитель, соединение, описания, модуль.
Проверено на железе (`maxwell --devices`):

- **Audeze Maxwell** (владеет RACE, тир Vendor) получил «Громкость Windows · Chat»
  и «· Game» **рядом** с аппаратной громкостью — ровно критерий готовности фазы 0;
- **HyperX QuadCast S** (владеет тир 0) получил рабочую микрофонную страницу:
  уровень записи, mute, громкость мониторинга.

Склейка идёт не по одному container id: драйвер Audeze нашёл гарнитуру через
HID-интерфейс и про контейнер ничего не знает, поэтому дополнитель пересчитывает
для контейнера конечной точки полный набор идентификаторов (container + usb + bt)
и пересекает с набором устройства. Виртуальные точки (`00000000-…-ffffffffffff`)
отбрасываются — иначе iVCam, NVIDIA Broadcast и Steam слиплись бы в одно
воображаемое устройство.

**Поправка после первого показа: вендорская страница остаётся вендорской.** Core
Audio встал на страницу Audeze — механизм сработал, а результат оказался неверным.
Гарнитура сама отвечает за свой звук (общая громкость, баланс чашек, уровень
микрофона, эквалайзер), и рядом с этим появился ползунок Windows для того же
железа. Оба числа настоящие, и это не одно и то же число, — страница перестаёт
читаться, как их ни подписывай.

Тиры это выразить не могут: тир решает, кто владеет устройством, а к моменту
запуска дополнителей владелец уже выбран. Не хватало способа владельцу сказать,
что он пускает добавлять. Это `DeviceInfo.Supersedes` — список id дополнителей,
чью землю драйвер уже покрывает; объявляет тот, кто нашёл устройство, потому что
только он и знает. Драйвер Audeze перекрывает `audio` и ничего больше: батарейный
усаж или что угодно ещё, что появится позже, по-прежнему приветствуется — RACE за
это не отвечает.

**Как смотреть классовую страницу на железе с вендорским драйвером.** Единственная
гарнитура на столе — Audeze, и её классовую страницу иначе можно было бы только
вообразить. Ключ `--no-vendor` выключает глубокие драйверы и оставляет классовые
протоколы — и в приложении, и в пробнике. С ним тот же Maxwell возвращается
обычным системным устройством: заряд по Bluetooth, громкости Game и Chat, уровень
записи. Это и есть базовая страница гарнитуры, снятая с железа:

```
Audeze Maxwell  [Headset]  Active
  key system:a5e9da54-…  driver system
  transport  USB / Bluetooth          audio only
  [Power]       Заряд                    95 %
  [Audio]       Громкость Windows · Chat 44 %   ·  Звук выключен · Chat   нет
                Громкость Windows · Game 40 %   ·  Звук выключен · Game   нет
  [Microphone]  Уровень записи           50 %   ·  Микрофон выключен      нет
```

**Перенесено из фазы 1 в фазу 4:** живой пик-метр. Опрос сейчас идёт раз в секунду,
а полоска уровня с частотой 1 Гц выглядит сломанной, а не живой. Быстрая дорожка
нужна и пик-метру, и диагностике стиков геймпада — делаем её один раз в фазе 4 и
включаем обе.

## 6. Границы: что честно не сделаем

- **Заряд наушников и клавиатур по 2.4G-донглу** — донгл его не выставляет.
  Только вендорский протокол или Bluetooth-спарка.
- **VIA через донгл** — не выставляется. Снимок с датой, а не иллюзия правки.
- **DPI и подсветка мышей не-Logitech** — у Razer, Glorious и прочих свои
  закрытые протоколы, класса нет.
- **Лепестки геймпадов** — их нет в XInput ни у кого, включая Xbox Elite.
- **Ремап на борту у Switch Pro** — протокол не предусматривает.
- **Программный слой ремапа** (ViGEmBus и HidHide, как reWASD) — универсально
  решает лепестки и макросы для любого пада, но это установка драйвера и
  постоянный перехват. Стратегическое решение уровня продукта, не фича этого
  плана.
- **Кодек Bluetooth, аппаратные эффекты, прошивка сторонних** — вендорское.

## 7. Риски

| Риск | Оценка | Что делаем |
|---|---|---|
| Механика дополнителей окажется не той абстракцией | Средний | Держим её на одном методе; первый же реальный дополнитель (`audio`) проверит форму до того, как их станет четыре |
| Запись в HID++ уносит настройки мыши | **Высокий** | Лейаут `0x2202` сверяем с Solaar до первой записи; всё пишем со статусом `Untested`; DFU и `[hidden]`-фичи не трогаем вообще |
| Живая диагностика геймпада роняет частоту UI | Средний | Только при открытой странице, отдельный интервал, замер до включения по умолчанию |
| Core Audio плодит строки-дубликаты | Средний | Склейка по `ContainerId`; выход без совпадения — отдельная строка, а не привязанная наугад |
| Конвейер VIA-определений раздувает сборку | Низкий | В бандл — компактный индекс, определения докачиваются по требованию и кэшируются |
| Пишем драйверы против железа, которого нет | Средний | Тесты на документированных байтах до устройства — метод уже сработал на `SwitchPro.cs` |

## 8. Проверки у стола, без которых часть работ слепая

Дополняют [VERIFY-LATER.md](VERIFY-LATER.md), не заменяют:

1. **Кабель к Air96** — без него фаза 6 пишется вслепую (VERIFY-LATER п. 10).
2. **Док Flydigi: какой байт чей** — блокер модуля `flydigi` (п. 1).
3. **HID++ по Bluetooth** — спарить мышь по BT и посмотреть, отвечают ли
   коллекции `0xFF00`. Определяет, покрывает ли фаза 3 BT-транспорт.
4. **Сканер батарейных усажей** — прогнать по всему столу и увидеть, кто их
   объявляет. Ответ решает, стоит ли фаза 2 своего места в очереди.
5. **QuadCast: tap-mute и ручка** (п. 2) — определяет, будет ли строка mute
   у микрофона.

## 9. Ветка и шаг 0

Работа ведётся в `feature/base-devices`, отведённой от `feature/devices-hub`.

**Перед отведением надо разобраться с незакоммиченным.** В рабочем дереве
`feature/devices-hub` сейчас около сорока изменённых файлов — эквалайзер,
планировщик опроса, события с устройства. Среди них `DeviceSession.cs`,
`IDeviceDriver.cs`, `PollingPolicy.cs` и `DevicePollingScheduler.cs` — ровно те
файлы, которые фаза 0 переписывает. Отвести ветку от коммита и потерять их из
базы значит гарантировать конфликты.

Рекомендация: сначала закоммитить готовое в `feature/devices-hub`, затем
отвести от него `feature/base-devices`.
