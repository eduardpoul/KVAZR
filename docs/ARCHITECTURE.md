# Архитектура: формат под реализацию всех устройств

Как устроен проект, чтобы поддержка новых устройств добавлялась предсказуемо —
общие драйверы по классу отдельно, глубокие по устройству отдельно, — и чтобы
память тратилась там, где это имеет смысл.

## Два вида драйверов, две папки

```
src/Maxwell.Core/Drivers/
  Shared/          ← общие: один протокол на целый класс/семейство
    Logitech/        HID++ — все мыши/клавы/трекболы Logitech
    (Gamepad/)       XInput + падовые протоколы  — план
    (Audio/)         Core Audio — уши/микро/колонки — план
    (Keyboard/)      VIA/QMK — план
  Device/          ← глубокие: один вендорский протокол, «как одизи»
    Audeze/          RACE
    (Flydigi/)       Space — план (см. FLYDIGI-APEX5.md)
    (Nintendo/)      Switch Pro — протокол готов (SWITCH-PRO.md)
  System/          ← ядро: tier-0, всё что видит Windows
  Mock/            ← тестовые устройства для разработки UI
```

Правило деления простое: **Shared** — если один код покрывает много моделей
разных даже вендоров (класс-протокол). **Device** — если это реверс одного
вендора ради глубины, окупающийся только для его линейки.

Namespace плоский (`Maxwell.Core.Drivers.Logitech`, `.Audeze`) — папки для
глаз, namespace для смысла; уровень `Shared/Device` в имя типов не тащим
(и `Class`/`Shared` вообще зарезервированные слова в .NET-языках).

## Модуль — единица подключения

Каждая папка драйвера несёт `IDriverModule` — самрегистрацию. Он один метод:
кладёт свои драйверы в контейнер, платформу-неподходящую тихо пропускает.

```csharp
public sealed class LogitechModule : IDriverModule
{
    public string Name => "logitech";
    public void Register(IServiceCollection services)
    {
        if (!OperatingSystem.IsWindows()) return;
        services.AddSingleton<IDeviceDriver, HidPlusPlusDriver>();
    }
}
```

Композиционный корень (`Program.cs`) перечисляет модули **одной строкой на
семейство**:

```csharp
builder.Services.AddDeviceRegistry(
    includeMockDevices: true, mockDeviceCount: mocks,
    new AudezeModule(),
    new LogitechModule());
    // + new NintendoModule(), new FlydigiModule() … по мере готовности
```

Ядро не знает ни одного драйвера по имени, драйвер не знает другого. Новое
устройство = папка + модуль + строка. Ничего больше не двигается.

**Почему папки, а не отдельные .csproj.** Пробовать отдельные сборки под
каждый драйвер — оверинжиниринг на этом масштабе: сборки нужны ради изоляции
зависимостей и раздельной поставки, а здесь у всех драйверов одни и те же две
зависимости (контракт + транспорт), и поставка одна. Папка + модуль дают ту же
разделённость логики без веса. Если однажды понадобится плагин извне (чужой
драйвер отдельной поставкой) — `IDriverModule` уже готов принять его из внешней
сборки, менять придётся только способ обнаружения модулей, не сами драйверы.

## Как драйвер встаёт в систему (контракт)

Драйвер реализует `IDeviceDriver`: `DiscoverAsync` (кого нашёл, дёшево, без
открытия хендлов) и `ConnectAsync` (открыть на чтение/запись). Реестр
(`DeviceRegistry`) делает остальное сам:

- **Tier** решает конфликты. `System` (0) находит всё; `Class` — протоколы;
  `Device`/`Vendor` — глубокие. Нашли одно железо два драйвера → выше тиром
  побеждает, ниже отбрасывается. Так «USB Receiver» из tier-0 уступает мыши
  из HID++.
- **HardwareIds** склеивают. Драйвер несёт id железа (`usb:…`, `bt:…`,
  `hidpp:…`); совпали — одна строка с двумя транспортами. Так донгл и BT
  одной клавы сливаются.
- **Capabilities** описываются на краю драйвера и дальше живут абстрактно —
  UI строится из них, драйвер внутри строго типизирован. «Первая запись»
  помечается янтарём (Untested), пока живое устройство её не подтвердит.

Данные — не код: имена/фото/иконки/доки моделей в `Catalogue/devices.json` и
генераторах (`tools/*.py`), не в драйверах. Драйвер добавляет протокол;
модель добавляет строку данных.

## То же для UI: Web-компоненты по ролям

```
src/Maxwell.App/Web/
  Pages/            страницы: Dashboard, Device, Settings, Hotkeys, About
  Controls/         переиспользуемое: CapRow, Thumb, Battery, Dropdown, ReactiveComponent
  Infrastructure/   хост и клей: PaneHost, PaneRoot, WebUi, WebAssets, DeviceIcon, FluentIcons.g
  _Imports.razor
```

Namespace всех Blazor-компонентов плоский (`@namespace Maxwell.App.Web`) —
папки не ломают межкомпонентные ссылки. Новый контрол → в `Controls/`, новая
страница → в `Pages/`.

## Память: где экономить, где нет

Главный вопрос — что держать в памяти, когда приложение живёт в трее. Честный
разбор по потребителям:

| Потребитель | Размер | Выгружать? |
|---|---|---|
| Модели устройств (снимки, capabilities) | **килобайты** на устройство, десятки КБ на всех | **Нет.** Ленивая выгрузка данных такого размера — сложность без выигрыша. Держим всё. |
| Код драйверов | сотни КБ | **Нет.** Выгрузка сборок (AssemblyLoadContext) не окупается на порядок. |
| Фото устройств (data-URI в вебе) | ~сотни КБ каждое | Лениво **грузить** по требованию (уже: `WebAssets` кэширует по ключу), не держать все заранее. Выгружать не обязательно. |
| **WebView2 (контент-панель)** | **~300 МБ, 6 процессов** | **Да — вот где вся экономия.** |
| HID/BT хендлы | ядро ОС | **Не держать открытыми.** Открывать на операцию, закрывать. |

**Вывод одной фразой:** данные устройств настолько малы, что их ленивая
выгрузка — пустая трата усилий; вся реальная экономия в **WebView и в хендлах
железа**, и только там стоит стараться.

Конкретные политики (частью уже сделаны, частью — план, помечено):

1. **WebView — ленивое создание и разрушение.** *(план)* Сейчас `PaneHost`
   поднимает WebView при старте окна. Правильно: не создавать, пока окно ни
   разу не показано (в трее вебвью не нужен вовсе — там только иконка и меню);
   и **разрушать** при долгом сворачивании в трей (таймер, напр. 5 мин),
   пересоздавая при следующем показе. Пересоздание ~2 сек — приемлемо для
   редкого события, а отдаёт 300 МБ. Это единственная крупная память приложения
   и единственное, ради чего стоит городить lazy-логику.

2. **Хендлы железа — на операцию, не в держку.** *(уже так у Logitech/System)*
   Канал открывается на чтение и закрывается. Держать открытыми хендлы всех
   устройств — это и контеншн с родным софтом (G HUB, Space), и утечки на
   отключениях. Опрос раз в 30 с не требует постоянного хендла.

3. **Фоновый опрос — дросселируется вниманием.** *(уже так)* В трее
   `PollingAttention.Idle` держит тёплой только батарею; полный разбор
   capability — только когда окно открыто (`Glance`) и страница устройства
   активна (`Activate`/`Deactivate`). Открытая страница читает своё устройство
   часто, скрытые — редко.

4. **Драйвер-соединения — по визиту.** *(уже так)* `DevicePageViewModel`
   поднимает соединение при открытии страницы и гасит при уходе; на дашборде
   живут только дешёвые снимки, не открытые протокольные сессии.

Что сознательно НЕ делаем: не выгружаем модели, не выгружаем сборки, не
закрываем реестр в трее. Их суммарная память — единицы МБ, а сложность
управления жизненным циклом всего этого дороже, чем 2–3 МБ.

## Чек-лист «добавить устройство»

**Класс-протокол** (Shared): новый драйвер `IDeviceDriver` с `Tier=Class`,
модуль `IDriverModule` рядом, строка в композиции; capabilities мапятся из
самоописания протокола (как HID++ читает FeatureSet). Ноль данных на модель.

**Глубокое устройство** (Device, «как одизи»): протокол в `Maxwell.Race/
<Vendor>/` + тесты на документированных байтах (образец — `SwitchPro.cs`),
драйвер+соединение в `Drivers/Device/<Vendor>/`, модуль, строка в композиции,
запись в каталог (имя/фото/иконка), флаг `unverified` до живого подтверждения.

**Данные модели** (без кода): строка в `devices.json` — имя, фото, донгл/док,
hidden. Достаточно, чтобы устройство красиво показалось даже без драйвера.
