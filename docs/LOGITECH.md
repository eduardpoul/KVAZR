# Logitech HID++ — что мышь отдаёт и что у неё можно менять

Замер 25 августа 2026 на Logitech G Pro X Superlight 2 — через приёмник
(`046D:C54D`) и по кабелю (`046D:C09B`), результат одинаковый. Всё прочитано
командами, ничего не записано.

```
dotnet run --project src/Maxwell.Cli -- --hidpp          # имя, заряд, таблица, разрешение
dotnet run --project src/Maxwell.Cli -- --hidpp --deep   # плюс первый вопрос каждой возможности
```

## Почему это не заточка под одну мышь

HID++ 2.0 **самоописывающийся**. У устройства есть таблица возможностей, и сам
перечень — тоже возможность: мышь можно **спросить**, что она умеет, а не
перебирать наугад. Драйвер не знает про Superlight 2 — он читает таблицу и
объявляет строки по тому, что в ней есть.

Поэтому одна реализация покрывает всю линейку Logitech, включая модели, которых
ещё нет. Разница между поколениями — в номерах возможностей: у старых мышей
разрешение `0x2201`, у новых `0x2202`; частота опроса `0x8060` против `0x8061`.
Драйвер должен уметь обе пары и брать ту, что объявлена.

## Что читается

Проверено на живой мыши, ответы приведены как есть.

| возможность | ответ | что это |
|---|---|---|
| `0x0005` | `07 …` | имя («PRO X 2») и тип (мышь) |
| `0x1004` | `0F 0F 02` | заряд и признак зарядки |
| `0x0003` | `02 2121B490 000C 40A9C09B…` | 2 прошивочных блока, **unit id `2121B490`**, транспорт, model id |
| `0x8100` | `01 07 01 05 01 **05** 10 00FF 0A 04` | 5 профилей, формат 7, и **пять кнопок** |
| `0x8110` | `05` | те же пять |
| `0x2202` | см. ниже | разрешение целиком |
| `0x8061` | `00 0F 00` | битовая маска поддерживаемых частот — четыре |

**Разрешение, `0x2202`, по функциям:**

```
fn 0  01                              один сенсор
fn 1  00 050F                         его возможности
fn 2  00 00 0064 E001 00C8 E002 01…   диапазон: от 100 шагом 1 до 200, дальше шагом 2
fn 3  00 00 0320 04B0 0640 0960 0C80  пресеты: 800, 1200, 1600, 2400, 3200
fn 4  00 02 02 02 02 02               список высот отрыва
fn 5  00 0320 0320 0320 0320 02       текущее 800, по умолчанию 800, LOD 2
```

**Два вывода, которые стоят отдельно.**

**Настоящее число кнопок.** `0x8100` отдаёт `buttonCount = 5`, и `0x8110`
подтверждает. Дескриптор HID у этой мыши объявляет шестнадцать, и Windows
повторяет шестнадцать (см. `docs/MICE.md`). То есть у Logitech — и только у неё —
число кнопок вообще узнаваемо.

**Серийный номер.** `unit id` из `0x0003` — единственный способ различить две
одинаковые мыши. Ни дескриптор, ни Windows его не дают.

## Частота опроса

Две половины из двух источников, и только одна из них — знание, хранимое у нас.

**Какие частоты вообще бывают** — это словарь протокола: семь штук, от 8 мс до
125 мкс, в фиксированном порядке битов. Это справочник, а не ответ устройства.

**Какие из семи предлагает эта мышь** — ответ устройства, и он разный по линкам:

```
маска, линк 0   0x000F   →  125, 250, 500, 1000 Гц
маска, линк 1   0x007F   →  125 … 8000 Гц
текущая         03       →  1 мс = 1000 Гц
```

Номера функций взяты не из памяти: чтение — функция 2, запись — 3, по
[реализации Solaar](https://github.com/pwr-Solaar/Solaar). До того я дошёл
измерением до функции 1 и остановился — там, где у разрешения страховкой был
нижний край диапазона (ноль вне его), здесь такой страховки нет: индекс 0 вполне
может оказаться допустимой частотой, и промах на единицу поменял бы человеку
настройку. Прочитать описание оказалось дешевле, чем угадывать на чужой мыши.

Какой из двух списков показывать — определяется тем, как мышь подключена, и это
пришлось чинить. Правило «тот список, в котором есть текущая частота» выбирало первый
всегда: 1000 Гц есть в обоих. Мышь на донгле получала список из четырёх частот, хотя её
линк предлагает семь. Проверено записью — 2000 Гц она приняла и отчиталась о них, а 2000
есть только в длинном списке:

```
fn 0, линк 0   000F   →  125, 250, 500, 1000
fn 0, линк 1   007F   →  125 … 8000
fn 2, любой    03     →  1000 Гц — одинаково, линк по нему не узнать
fn 0, линк 2          →  неверный аргумент, линков ровно два
```

Отвечает на своём индексе — значит на кабеле, отвечает через слот приёмника — значит по
воздуху. Беспроводную половину доказали те 2000 Гц; проводная — по остатку.

## Что меняется

| | как |
|---|---|
| **разрешение** | `0x2202` fn 6, значения из fn 3 или любое из диапазона fn 2 |
| **частота опроса** | `0x8061`, из маски fn 0 |
| **профили** | `0x8100` — пять профилей, свой формат памяти; отдельная работа |
| высота отрыва | в тех же параметрах, что и разрешение |

## Запись разрешения: отказ, и почему

Первая попытка записи — измерена, ничего не изменилось.

```
before   800 DPI, lift-off 2
mode     1 (свой бортовой профиль)
         не реализовано
write    refused
```

Функция шесть возвращает «не реализовано», хотя функция пять рядом прекрасно
читает. Причина не в номере функции: **мышь живёт по своему бортовому профилю**
(`0x8100`, режим 1), а устройство, играющее по собственной записи, не обязано
принимать настройку с компьютера. Отказ при этом выглядит ровно как отсутствие
функции.

Чтобы разрешение писалось, мышь надо перевести в режим «настройки с компьютера»
(`0x8100`, функция 1, значение 2). Это не деталь реализации, а смена поведения:
кнопка переключения DPI на самой мыши перестаёт применять её сохранённый профиль,
и настройки начинают приходить снаружи. Именно это делает G HUB, когда двигают
его ползунок. Обратимо — режим 1 возвращает как было.

Номера функций режима: чтение — 2, запись — 1, по реализации Solaar.

## Настройки лежат в самой мыши, и туда можно писать

Отказ выше был верным наблюдением и неверным выводом. Если бы G HUB переводил мышь
в режим «с компьютера», его настройки умирали бы вместе с ним. Мы же видим
обратное: G HUB закрыт, режим = 1 (свой профиль), а в мыши лежат выставленные в нём
800 DPI и 1000 Гц. Значит G HUB **правит бортовой профиль**, а не забирает мышь из
него. Туда же должны писать и мы — иначе наши настройки тоже не переживут закрытия.

**Как устроена память.** Функции `0x8100`: чтение сектора — 5 (по 16 байт со
смещением), начало записи — 6 (сектор и длина), данные — 7, конец — 8.

```
директория (сектор 0)   000101FF 000200FF 000300FF 000400FF 000500FF FFFF…
                        сектор 1 включён, 2…5 выключены

профиль (сектор 1, 255 байт)
  03            частота: индекс 3 = 1000 Гц  — сходится с 0x8061
  03 00 00      …
  2003 2003 02  800 / 800, высота отрыва 2
  B004 B004 02  1200
  4006 4006 02  1600
  6009 6009 02  2400
  800C 800C 02  3200                          — сходится с пресетами 0x2202
```

Пять записей по пять байт: разрешение поперёк, разрешение вдоль, высота отрыва —
и всё это младшим байтом вперёд, в отличие от остального протокола.

**Контрольная сумма — пропуск к записи.** CRC-16/CCITT от `0xFFFF` по первым 253
байтам, big-endian в последних двух. Наша сумма воспроизвела ту, что лежит в мыши,
байт в байт: `84DB` против `84DB`. Пока она не сходилась, писать было нельзя —
именно это отличает собранный сектор, который устройство примет, от такого,
который оно отвергнет или, хуже, возьмёт.

**Запись проверена.** В **выключенный** профиль, чтобы проверять было не на чём
ломаться: записали 1600 в первую позицию сектора 2, прочитали 1600, вернули 800 и
убедились.

```
before   800 DPI
wrote    1600 DPI
after    1600 DPI
restored 800 DPI
```

## Частота опроса: тоже в профиле, байт 1

Записывается так же, как разрешение, и по той же причине переживает закрытие
приложения.

```
before   byte 1 = 3, мышь сообщает индекс 3   (1000 Гц)
written  byte 1 = 2, мышь сообщает индекс 2   (500 Гц)  — сразу
restored индекс 3
```

**У профиля два байта частоты — по одному на вид подключения**, и на мыши, у
которой оба линка настроены одинаково, они читаются одинаково: различить их
чтением нельзя. Поэтому драйвер не решает, а **пробует**: пишет один, спрашивает
мышь, что она делает, и если та не сдвинулась — возвращает байт на место и берётся
за второй. Байт, который двигает мышь, и есть нужный.

Ниже — три пути, которые не сработали, и они остаются верными: прямой установщик
отвергает, байт 0 у этой мыши не тот, перечитывание профиля ничего не даёт.
Правильный путь нашёлся только потому, что второй байт заголовка тоже равнялся
трём и это показалось совпадением.

## Что не сработало и почему это стоит помнить

Разрешение меняется, частота — нет. Испробованы три пути, все на живой мыши, все с
возвратом.

**Прямой установщик.** Функция 3 у `0x8061`, один байт — индекс; форма сверена по
Solaar, не подобрана. Ответ: **«неверный аргумент»**. Не «не реализовано», как было
у разрешения, — то есть функция есть и отказывается именно от параметров или от
самого момента. У Solaar в описании этой настройки прямо сказано: *может
потребовать отключения бортовых профилей, чтобы подействовать*. Та же стена.

**Байт в профиле.** Первый байт профиля — частота, и он сходится с тем, что
отдаёт `0x8061` (оба 3 = 1000 Гц). Запись проходит, сектор принимает новое
значение — а мышь продолжает сообщать прежний индекс. Значит живая частота
читается не оттуда.

**Перечитать профиль.** Команды на это нет: Solaar после записи сектора ничего не
перезагружает, и в описании возможности такого не значится.

**Почему разрешение работает, а частота нет.** Возможность разрешения отвечает из
живого состояния, которое следует за сектором немедленно — это измерено. Возможность
частоты так не делает. Это устройство так устроено, а не пробел у нас.

Из этого был сделан вывод, что менять частоту нельзя, — и вывод оказался неверен.
Верно было только то, что перечисленными путями нельзя. Настоящий путь — байт 1
профиля, см. выше.

## Пять ступеней: как выбор из списка ставит мышь на значение

Строка «Разрешение» показывает пять значений — это лесенка, которую мышь перебирает
собственной кнопкой. Какая из пяти в силе — её собственное дело, и ничем найденным это не
задаётся, поэтому единственное, что меняет поведение мыши, — значение той ступени, на
которой она стоит.

Написанное в лоб это **теряет разрешение**. Так и вышло, на живой мыши, у человека:

```
было   800 DPI    ступени 800/1200/1600/2400/3200
стало 1600 DPI    ступени 1600/1200/1600/2400/3200     ← 1600 дважды, 800 нет
```

Поэтому ступени **меняются местами**. Мышь встаёт на нужное значение и по-прежнему хранит
все пять, что хранила, — изменился только их порядок, а порядок это и есть то, в какой
последовательности их обходит её кнопка. Значения, которого в лесенке нет, менять не с
чем, и оно просто записывается.

```
было   1200 DPI   ступени 1200/800/1600/2400/3200
стало  1600 DPI   ступени 1600/800/1200/2400/3200
назад  1200 DPI   ступени 1200/800/1600/2400/3200
```

Арифметика вынесена в `PointerWriter.Trade` и накрыта тестами отдельно от железа —
потому что ошибиться в ней можно беззвучно: запись проходит в обоих случаях, и устройство
не говорит ни слова, а платой становится тихо пропавшее разрешение.

**Переключить активную ступень не удалось.** Solaar называет байты заголовка профиля
`report_rate`, `resolution_default_index`, `resolution_shift_index`. У этой мыши байтов
частоты **два** (по одному на вид подключения), значит индекс сдвинут — и байты 2 и 3
подходят по смыслу. Ни один не двигает мышь: ни сразу, ни после перечитывания профиля, ни
после настоящей загрузки (режим 1 → 2 → 1). Похоже, живая ступень — энергозависимое
состояние, которое ставит кнопка на мыши, а байт 2 применяется только при включении.
Проверить это можно единственным способом: записать байт, **выключить и включить мышь**.

## Лесенка шагов — тоже вопрос к устройству

Диапазон разрешения приходит не как «от и до», а как ступенчатая шкала. Целиком:

```
100 … шаг 1 … 200 … шаг 2 … 500 … шаг 5 … 1000 … шаг 10 … 2000 … шаг 20 … 5000
    … шаг 50 … 10000 … шаг 100 … 20000 … шаг 125 … 32000 … шаг 200 … 44000
```

Около девятисот допустимых значений, мелко там, где люди работают, и грубо наверху. Мы из
всего этого берём только края (100 и 44000) — а для редактора ступеней нужна именно
шкала, и она у мыши есть, выдумывать нечего.

## Два читателя на одном устройстве: чья это строка

Страница назвала мышь «Logitech b» и управляющий символ следом. Байты оказались `62 08`
— это 98 и 8, а мышь в ту минуту показывала **98 % заряда**. Имя было прочитано из ответа
про батарею.

**Почему так вышло.** Запрос «где в таблице лежит возможность N» называет N в вопросе, а в
ответе приходит только индекс — что спрашивали, в нём не сказано. Значит два таких запроса
одновременно неотличимы, и любой из читателей забирает чужой ответ. Дальше всё честно:
поиску имени вернули индекс батареи, он спросил у батареи функцию 0 и функцию 1 и разобрал
показания заряда как буквы.

Измерено, а не выведено — проба `--crosstalk` держит два потока на одном устройстве:

```
до    40 раундов, обменялись ответами 40
после 60 раундов, обменялись ответами 0
```

**Чем чинится.** В протоколе для этого есть своё поле: младшая половина байта функции —
подпись того, кто спрашивает, и устройство возвращает её в ответе. Мы ставили туда одно
число на всё приложение. Оно отличало нас от G HUB и не отличало нас от нас самих: драйвер
открывает канал, чтобы познакомиться с устройством, опросник — свой, чтобы читать заряд, и
каждый отчёт приходит на оба дескриптора. Теперь подпись своя у каждого канала.

Замок внутри канала при этом ни при чём и был не виноват: он разводит два запроса **в
одном** канале, а беда была между двумя каналами.

Поверх этого — проверка на здравый смысл: имя модели это печатный текст, и строка с байтом
ниже пробела именем не считается. Она не лечит причину, а страхует от чужой программы,
подписавшейся так же, как мы.

## Границы, установленные измерением

- **Функции-записи не вызывались ни разу.** Обход спрашивает только функцию 0 —
  она во всех возможностях HID++ является запросом, а всё, что меняет, лежит
  дальше по списку. Для `0x2202` дошли до fn 5 пошагово: каждый следующий вопрос
  задавался после того, как предыдущий ответил ровно так, как предсказывала
  раскладка.
- **Половина возможностей молчит.** `0x1801`, `0x1802`, `0x1830`, `0x1861`,
  `0x18A1` и прочие отвечают «не реализовано» на функцию 0 — это уведомления и
  сервисные вещи, у которых первой функции нет.
- **`0x1D4B`** отвечает ошибкой: тоже только уведомления.

## Чем это кончилось: что на странице мыши

| строка | откуда | пишется |
|---|---|---|
| **Разрешение** | живое из `0x2202` fn 5, список — из лесенки профиля | да, обменом ступени, на которой мышь стоит, с той, где лежит выбранное |
| **⋯ пять ступеней** | те же пять записей профиля | да, одной записью сектора, из диалога за карандашом |
| **Частота опроса** | `0x8061` fn 2, список — маска того линка, на котором мышь | да, байт 1 профиля (или 0, что подойдёт) |
| Кнопок | `0x8100` fn 0 | нет — паспорт |
| Профилей на борту | `0x8100` fn 0 | нет — паспорт |
| Серийный | `0x0003` unit id | нет — паспорт |

Три вещи стоит помнить о том, как это устроено, потому что ни одна не очевидна.

**Список разрешений — это показание, а не меню.** Пять ступеней и есть варианты
строки «Разрешение», и они же — отдельная настройка. Объявленные один раз при
знакомстве, эти два расходились с первой же правкой: строка продолжала предлагать
ступень, которой в мыши уже нет. Драйвер теперь называет возможность, из которой
берётся список (`ChoicesFromCapability`), а сессия разрешает его каждую публикацию
— тем же приёмом, каким потолок ползунка берётся из чужого показания.

**Ползунки ступеней живут в диалоге, а не на странице.** Пять дорожек, лежащих
открытыми, — это пять способов записать во флеш мыши, задев их рукой. За кнопкой,
с «Сохранить», их правят намеренно или никак; группа при этом придерживает записи,
пока диалог открыт, иначе «Отмена» отменяла бы уже записанное.

**Окно ползунка — 200…5000 с шагом 200 — выбрано человеком, а не мышью.** Мышь
отдаёт 100…44000, и дорожка через весь этот размах — дорожка, где один пиксель
это сто семьдесят DPI. Оба края окна лежат на изломах её же лесенки, и все
привычные значения кратны шагу, так что каждое положение допустимо. Окно ужимается
под меньший диапазон и расширяется, чтобы вместить то, что в мыши уже записано.

## Что осталось недостижимым

**Переключить, которая из пяти ступеней в силе.** Solaar называет байты заголовка
профиля `report_rate`, `resolution_default_index`, `resolution_shift_index` — а у
этой мыши байтов частоты два, по одному на вид подключения, значит индекс сдвинут
на байт 2 или 3. Ни один не двигает мышь: ни сразу, ни после перечитывания сектора,
ни после настоящей загрузки профиля (режим 1 → 2 → 1). Похоже, живая ступень —
энергозависимое состояние, которое ставит кнопка на самой мыши, а байт 2
применяется только при включении. Проверяется единственным способом: записать байт
и **выключить-включить мышь**. Не проверено.

Пока этого нет, «Разрешение» меняет две ступени местами — см. выше. Значения при этом
целы, но их порядок в лесенке не тот, в котором их поставили, и кнопка на мыши обходит их
в новом порядке. Настоящее переключение сделало бы и это ненужным.
