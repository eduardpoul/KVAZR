# Классовые протоколы: как сделать поддержку автоматической

Ответ на вопрос «как VIA и прочее сделать автоматическим и универсальным».
Ключевая рамка: у каждого протокола есть **самоописывающаяся** часть (устройство
само говорит, что умеет — код универсален) и **данные-со-стороны** (без которых
часть UI не построить). Автоматизация = выжать максимум из первой и наладить
конвейер для второй. Данные — никогда не код: тот же принцип, что у нашего
каталога устройств.

---

## VIA (QMK-клавиатуры) — usage page 0xFF60, usage 0x61

Протокол поверх raw HID, 32-байтные отчёты, запрос-ответ. Текущие версии
протокола — v9–v12 (v12 актуальна). Поддерживается сотнями клавиатур из
коробки: NuPhy, Keychron, GMMK, почти весь кастом.

**Само устройство отвечает (универсально, ноль данных):**

| Что | Команда | Заметка |
|---|---|---|
| Версия протокола | 0x01 | рукопожатие и выбор диалекта |
| Число слоёв | dynamic_keymap get_layer_count | |
| Кейкод любой клавиши | get_keycode(layer,row,col) | чтение и **запись** |
| Весь кеймап разом | get_buffer | быстрее поштучного |
| Макросы: число и буфер | macro get_count / get_buffer | чтение и запись |
| Подсветка | custom-каналы: qmk_backlight, qmk_rgblight, qmk_rgb_matrix | яркость/эффект/цвет, чтение и запись |
| Матрица нажатий (live) | keyboard_value: switch_matrix_state | «тестер клавиш» бесплатно |
| Uptime, layout options | keyboard_value | |

**Чего в протоколе нет — и откуда это берут все:**

Физическая раскладка (какая матричная позиция = какая клавиша и где она
нарисована) в протоколе **отсутствует**. VIA-приложение берёт её из JSON-
определений:

- Репозиторий `the-via/keyboards` (GitHub, MIT) — тысячи определений,
  сопоставление по VID:PID. Это и есть «автоматика» VIA: подключил → нашли
  определение по id → нарисовали клавиатуру.
- Вендоры вне репы (NuPhy — частично) публикуют свои JSON для сайдлоада.

**План для нас (полностью повторяет нашу же схему с иконками/токенами):**

1. `tools/via-definitions.py`: качает `the-via/keyboards`, собирает компактный
   индекс VID:PID → определение, кладёт в ресурсы. MIT — бандлим с указанием
   источника. Обновление = перезапуск скрипта.
2. Рантайм-фолбэк: определения нет в бандле → одна попытка скачать по VID:PID
   из того же репозитория (сырой GitHub), кэш на диск. Офлайн → пункт 3.
3. Без определения драйвер ВСЁ РАВНО полезен: слои, макросы, подсветка,
   тестер нажатий — это протокол, не JSON. Нет только рисунка клавиатуры
   (для кеймапа нужны размеры матрицы, их тоже нет в протоколе). Кнопка
   «импортировать JSON» закрывает хвост.

**Vial — важная вилка.** Форк VIA, тот же 0xFF60: устройство хранит своё
определение **в самой прошивке** (сжатый JSON, вычитывается протоколом).
Vial-клавиатура самоописана полностью — рисунок без всяких баз. Поддержать
оба диалекта в одном драйвере: рукопожатие Vial → определение из устройства;
иначе VIA → определение из базы. Стоковая NuPhy — VIA (не Vial), так что
конвейер определений всё равно нужен.

**Ограничение, проверенное на столе трижды:** NuPhy не выставляет 0xFF60 через
2.4G-донгл — VIA работает только по кабелю (и это общий случай для донглов).

**Кабельная сессия + снимок — рабочая модель для донгла.** Важно понимать, где
живёт раскладка: dynamic keymap, макросы и настройки подсветки QMK хранит
**в памяти самой клавиатуры**. По донглу всё это ПРИМЕНЯЕТСЯ всегда — слои
переключаются, макросы играют, кабель нужен только чтобы читать и менять.
Отсюда модель:

1. Клавиатура появилась по кабелю → драйвер читает всё (кеймап-буфер, макросы,
   свет, число слоёв) и **сохраняет снимок** под ключом устройства.
2. Клавиатура на донгле → страница показывает снимок в read-only с датой
   («раскладка от 21.08») и строкой «подключите кабель, чтобы изменить» — тот
   же язык честности, что и «обновлено 14:41» на дашборде.
3. Новая кабельная сессия обновляет снимок.

Это не обход ограничения, а его честное оформление: врать «редактируемо» по
донглу нельзя, но и прятать известную раскладку глупо.

**API самого донгла NuPhy** — стандартного функционала нет совсем (ни VIA, ни
батарейных усажей: подтверждено дампами). Есть только закрытый канал 0xFF31 —
запрос-ответ, на прослушивание молчит; что он умеет (заряд? статус линка?),
покажет лишь реверс трафика NuPhy Console. До тех пор донгл для нас — «клава
печатает, настройки читаются из снимка».

## HID++ (Logitech) — эталон самоописания

Уже в приложении. Автоматика здесь образцовая, потому что протокол сам так
устроен: **таблица фич читается из устройства** (0x0001 FeatureSet), драйвер
мапит известные id на контролы, неизвестные пропускает. Ни одной строчки на
модель: PRO X 2 отдала 33 фичи, и любая другая мышь/клава Logitech отдаст свои.

Подтверждено живьём сегодня: частота опроса 0x8061 читается (сейчас 1 кГц),
прошивка 0x0003 читается; лейаут ответа DPI 0x2202 при реализации сверить с
Solaar (наш первый парс кривой — raw в пробнике оставлен для сверки).

Очередь того же драйвера: DPI, частота, режим питания, профили 0x8100.

## Стандартные HID-усажи — недокопанная универсальная дверь

HID имеет **стандартные** страницы, которые устройство декларирует в
дескрипторе — читаются без единого вендорского байта:

| Страница | Что даёт | Статус у нас |
|---|---|---|
| 0x000B Telephony | mute/off-hook гарнитур и микрофонов | найдена у QuadCast; слушатель готов (--live) |
| 0x0006 Generic Device Controls, usage 0x20 Battery Strength | **заряд как HID-значение** | не сканировали — добавить в сканер: перечислять value caps всех коллекций |
| 0x84/0x85 Power/Battery pages | заряд/зарядка ИБП-стилем | туда же |
| 0x000C Consumer | медиа-клавиши, ручки | событийно, слушатель готов |

Пункт про Battery Strength — конкретное действие: расширить сканер чтением
capability-массивов (HidP_GetValueCaps) по всем коллекциям устройства. Любой
девайс, объявивший батарейный усаж, получит заряд автоматически. Это дёшево и
строго универсально.

## Bluetooth LE: GATT Battery Service (0x180F)

Для спаренных LE-устройств заряд стандартен — Windows сам читает BAS и кладёт
в свойство узла (наш tier-0 это уже показывает). Плюс некоторые вещают 0x180F
прямо в рекламе — пробник `--airpods` теперь ловит и это (универсальная ветка
рядом с эппловской).

Apple — исключение: BAS нет, только фирменная реклама 0x07 (декодер готов).

## Сводная таблица: универсально или нет

| Находка | Универсальность |
|---|---|
| Core Audio (громкости/mute/пик) | ✅ любой звук любого вендора |
| Телефонный mute | ✅ механика стандартная; наличие — по устройству (у QuadCast есть) |
| HID++ (весь стек) | ✅ вся экосистема Logitech, самоописание |
| VIA | ✅ протокол; рисунок клавиатуры — из MIT-базы определений (конвейер) |
| Vial | ✅ полное самоописание из прошивки |
| XInput (подключение, вибрация) | ✅ всё Xbox-совместимое |
| BT-заряд (classic property / LE GATT) | ✅ стандарт |
| HID Battery Strength | ✅ стандарт; надо досканировать value caps |
| BLE-реклама 0x180F | ✅ стандарт; ловим |
| Реклама Apple 0x07 | вендор Apple, но покрывает все AirPods/Beats разом |
| Кадры дока Flydigi (5A A5) | вендор Flydigi (вероятно, всё их семейство) |
| RGB QuadCast (0xFF90) | вендор HyperX; формат известен из OpenRGB |
| NuPhy 0xFF31 | вендор NuPhy, протокол закрыт |
| RACE | вендор Audeze |

## Архитектура автоматики — три конвейера данных

Код — на протокол, данные — на модель, и данные текут по конвейерам:

1. **Определения VIA**: `tools/via-definitions.py` → бандл-индекс → рантайм-
   дофетч → импорт вручную. (Как fluent-icons.py и design-tokens.py.)
2. **Наш каталог** (devices.json): имена, фото, донглы/доки, hidden — уже есть.
3. **Самоописание**: HID++ FeatureSet, Vial, HID-дескрипторы, GATT — данные
   присылает само устройство, конвейер не нужен.

Новый девайс подключился → сканер находит двери по usage page → классовые
драйверы поднимают то, что устройство само о себе говорит → конвейеры
докладывают рисунки и имена. Ни один из шагов не требует «допилки как с
одизи» — она остаётся только для закрытых вендорских протоколов.
